## 三、数据层

### Room：只有 4 张表（文档 §13 列了 13 张）

| 表 | 装什么 | 备注 |
|---|---|---|
| `sessions` | 一段对话 + 它的会话级设置 | 遮罩三列在 **v6** 加入 |
| `messages` | 消息（含图片 data URL、思考过程、思考用时） | **写入后永不修改** |
| `sse_wal` | 流式预写日志 | 不进请求前缀，所以**每块都写**（崩溃恢复的基础） |
| `memories` | 长期记忆 | 归属**单段会话**（见第六节） |

其余 9 张（`users` / `market_*` / `memory_vectors` / `cache_*`）随各自功能再加 ——
一次建全只会得到一个"大部分表永远空着"的库，却要一次性承担全部迁移风险。

### 迁移纪律（**硬性**）

1. **绝不使用 `fallbackToDestructiveMigration()`** —— 代价是用户更新一次、对话全归零；
2. 手写 `Migration(n, n+1)`，SQL 与 Room 导出的 schema **逐字段核对**
   （`app/schemas/…/<n>.json`）；
3. 新增列一律**可空、不带 DEFAULT**：非空列在 `ALTER TABLE` 时必须带 DEFAULT，
   而 `@ColumnInfo(defaultValue = …)` 会让 Room 的 KSP 处理器去反序列化 schema bundle，
   与项目的 kotlinx-serialization 版本冲突（实测 `AbstractMethodError`）。
   默认值统一在 `SessionMapper` 里落定，**只此一处**；
4. **改了 `@Entity` / `@Dao` 之后必须干净构建** —— 见下面的构建地雷。

### ⚠️ 构建地雷：Room × kotlinx-serialization

`Room 2.8.x` 的 `room-migration` 字节码与 classpath 上的 serialization 在 KSP 类加载器里错配，
报 `AbstractMethodError: FieldBundle$$serializer … typeParametersSerializers()`。

**这个雷只在 KSP 真正处理 Room 时才炸**，而增量编译会跳过那一刻 —— 所以它会潜伏很久
（前几轮"构建成功"都站在增量编译的沙子上）。

现状：**Room 锁在 2.7.2** + `resolutionStrategy.force` 把 serialization 钉在 1.7.3。
**别把 Room 升回 2.8.x。**

### DataStore

设置、人设、用户资料都在这里（`Store.kt`）。**加字段不需要迁移** ——
这是"设置类的东西不进 Room"这条分工的红利。

## 四、缓存纪律（本项目最贵的一课）

### 五层 Prompt

```
messages[] = [
  1. Global Prefix    全局规则（所有角色共享）
  2. Frozen Prefix    人设（昵称/性别/性格/自由设定）
  3. History          历史消息 + 开场白（持久化后字节不变）
  4. Appendix Delta   时间/状态/记忆（每轮追加）
  5. User Input       本轮输入
]
```

**缓存命中的是 `tools + system + messages` 的完整字节序列。**
所以上面 1–3 层必须**逐字节稳定**，4–5 层才是"每轮变化"的部分。

### 三条铁律

1. **变化的内容永远放尾部**
2. **已写入的内容不再改写，新内容只追加**
3. **记忆用压缩而非裁剪，用分层检索而非全量注入**

### 绝不能进稳定前缀

时间戳 · 会话 ID · 每轮重算的情绪状态 · 每轮重新总结的记忆。

**最隐蔽的陷阱**：同一轮内**多次计算**同一动态值（时间在"组装请求"与"写历史"两处分别生成）
→ 跨分钟不一致 → 前缀分叉 → **且延迟暴露**（几轮后才表现为命中率骤降）。
工程解法：动态值**单轮只生成一次**，由同一变量引用。

### 「什么会碰缓存」速查表（改代码前先查这张表）

| 操作 | 碰不碰缓存 |
|---|---|
| 改界面 / 布局 / 字号 / 背景 / 遮罩 | ❌ 不碰 |
| 改会话级设置（免打扰 / 置顶 / 思考开关 / 思考强度 / 背景 / 遮罩） | ❌ 不碰（它们不进 `messages`） |
| 换头像、改「我」的昵称 | ❌ 不碰（不进冻结前缀） |
| 导出备份 | ❌ 不碰（**只读**） |
| **改人设文字** | ✅ **会** —— 该人设**所有会话**的前缀从第 0 字节全碎 |
| **改全局前缀** | ✅ **会** —— **所有**会话失效 |
| **删除 / 重新生成消息** | ✅ **会** —— 从改动处起失效（界面上有橙色告知） |
| 切换模型 | ✅ **会** —— 全部未命中 |

## 五、流式生命周期

```
Idle → Streaming → Completed → Persisted
              ↓ 中断
        Interrupted → Recovered / Discarded
```

| 行为 | 流式期间 | 流式结束后 |
|---|---|---|
| UI 更新 | ✅ 每 chunk | ✅ 最终刷新 |
| 写 `messages` 表 | ❌ **禁止** | ✅ 原子性写入 |
| 写 `sse_wal` | ✅ 每 chunk | ✅ 标记已持久化 |
| 算前缀哈希 / 存快照 | ❌ 禁止 | ✅ |

**关键**：流式接收完毕**才**原子性持久化完整消息 —— 中途写入会造成历史不一致 → 下轮前缀错位。

**另外两条实现事实**：
- **首字看门狗**：SSE 的 keep-alive 心跳会不断刷新 OkHttp 读超时，所以"服务端什么都没发"
  也能一直挂着。30 秒内一个事件都没到就报错（`ChatViewModel.firstByteTimeoutMs`）。
- **思考用时**：记「第一块思考 → 第一块正文」的毫秒数，只上屏、**不进请求体**。

## 六、记忆系统

### 归属：**单段对话**（这一条与文档 §8 相反，是用户要的）

同一人设新开一段对话**不共享**记忆。
- `MemoryDao` 的两条查询都按 `sessionId` 过滤；
- `MemoryRepository.remember` **没有 `scope` 参数**（不给调用方选择的机会）。

文档 §8 的"三层隔离（persona 级跨会话共享）"**已被用户推翻**，不要去"修正"回来。

### 注入路径（只有一条）

```
MemoryRepository.appendixLines() → PromptEngine.plan(memories = …)
  → 用户消息体的 <appendix> 块（前缀末端）
```

**绝不能**拼进冻结前缀或历史。记忆进附录前必须 XML 转义。

### 自动提取是**旁路**

`MemoryExtractionScheduler` 每 60 秒醒一次，条件满足时让模型回头提炼。
它**只写 `memories` 表**，从不碰对话历史、从不碰冻结前缀 —— 所以不打断任何会话的缓存。

三道护栏（间隔 10 分钟 / 会话有更新 / 前台不在流式）在 `MemoryExtractionThrottle.shouldRun()`。

⚠️ **提取花的是用户自己的 API 额度**，所以间隔是**省钱**护栏，不要顺手调小。

## 七、界面层

### 结构

- **主界面五个 Tab**（消息 / 人设 / 市场 / 我的 / 关于）**不走导航库**，用 state 切换 ——
  切 Tab 不该进回退栈。Tab 容器是 `ui/main/MainScreen.kt`，内容在 `MainTabs.kt`。
- **子页面走 `NavHost`**（路由表在 `MainActivity.kt` 的 `Routes`）。

### 设计令牌：**唯一事实来源**

| 文件 | 管什么 |
|---|---|
| `theme/Color.kt` | 色板（**全部不透明**；半透明只在组件叠加时逐处决定） |
| `theme/Shape.kt` | 圆角与间距 |
| `theme/Type.kt` | 字号 / 行高 / 字重（**不指定颜色** —— 交给 colorScheme） |
| `theme/SoftUi.kt` | 卡片与输入框的规格收口（`YukiCardSpec`）、导航选中底色 |
| `theme/ChatBackground.kt` | 背景预设 + 遮罩风格 |
| `components/SoftPanelSurface.kt` | 「柔和卡片」材质（输入区与底栏共用） |

**契约测试**：`FlatCardThemeTest`、`DesignTokensTest`、`SoftUiSpecTest`、`ChatBackgroundTest`。
改令牌前先跑它们 —— 它们钉的是**结构事实**（色相区间、圆角范围、不透明），不是"好不好看"。

### ⭐ 关键手法：旧名**指向**新色板

`SnowWhite` / `SkyBlue` / `FrostLine` / `TextMuted` … 这些 v0.5.0 起就在用的名字**没删**，
而是全部改成**指向新色板**。于是所有组件的颜色自动跟随，**一行 View 代码都不用改**。
`DesignTokensTest` 钉住「别名与新值同值」，防止将来有人只改一边。

### 视觉：当前的定调是「**柔和卡片材质**」（v0.35.0）

| 要素 | 值 | 位置 |
|---|---|---|
| 底 | 径向渐变：`PanelBase`(#F7F8FA) → 暖米粉 `PanelWarmTint`(#FCEEE8) | `SoftPanelSurface` |
| 暖色位置 | 输入区**右上**、底栏**左下**（差异化） | 同上（`tintAnchor`） |
| 阴影 | 柔和弥散的**浅灰**（不是黑 —— 黑会发脏） | `PanelShadowTint` |
| 描边 | 极细（0.8dp）半透白，上亮下暗 | `SoftPanelSurface` |
| 圆角 | 输入区 36dp / 底栏 28dp | `Shape.kt` |

⚠️ **用户明确要求「不要背景模糊，不要玻璃拟态效果」** —— 所以底色**不透明**，
层次由「渐变 + 阴影 + 高光」表达，**不由透明度表达**。

> 这条纠正了项目的一贯路线：水彩、液态玻璃、v0.34.0 的输入框都在试图"靠透明度做层次"，
> 并因此在浅色底上反复翻车（白液滴隐形、低 alpha 胶囊不可见、白输入框叠白卡片，三次）。
> **不透明的东西不会隐形。**

### 聊天输入区（v0.35.0 规格）

```
┌──────────────────────────────────────────────┐
│ (＋)  输入框（透明底、浅灰占位）        (…) (…) │  ← 圆钮：附件 / 语音（待定）
│       [发送]  ← 小胶囊，靠左                    │
└──────────────────────────────────────────────┘
```
- 外壳：`SoftPanelSurface(corner = 36.dp)`，**不透明**
- 距底留白：**未聚焦 32dp / 键盘弹起 12dp**（用户要求"键盘弹起时仍保持悬浮"）
- 列表为此让出的高度：`INPUT_LAYER_RESERVED_HEIGHT = 112.dp`
  ⚠️ 它必须 ≥ 输入区实际高度（8 + 56 + 32 ≈ 96dp），否则最后一条消息会被压住

## 十、本机环境与限制（**别重复探测**）

| 事实 | 影响 |
|---|---|
| **无 adb 设备、无模拟器、无 system-images** | 一切真机验证都做不了。`adb devices` 输出为空可复核 |
| 物理内存约 2GB | 构建**必须** `--max-workers=1` |
| 构建副本必须在 **ASCII 路径** `<构建目录>` | AGP 拒绝含中文的路径 |
| Python 没有 PIL/Pillow | 要处理图片得先装 |
| 有 Edge，**没有 Chromium** | 视觉自查只能用 Edge headless 渲染**等价 HTML**（近似，证明不了真机渲染） |
| 一次构建约 3–8 分钟 | 一批一构建；构建超 120 秒 bash 会超时，**用后台任务跑** |

### 无设备时能做的验证（按可信度排序）

1. **JVM 单测**（416 个）—— 纯逻辑与契约，可复核；
2. **算术核对** —— 几何/预算类问题可以直接算（如"输入区 96dp ≤ 让出 112dp"）；
3. **静态核对** —— 如 `MigrationSchemaTest` 把"迁移 SQL"与"Room 导出的 schema"逐字段比，
   是官方 `androidTest` 迁移测试的**离线替代**；
4. ⚠️ **等价 HTML 渲染** —— 证明得了"形状/对比度对不对"，**证明不了真机渲染**，
   而且项目曾"做了复现却没看仔细，得出错误结论"（是用户截图把它翻过来的）。**用它时要比对得足够仔细。**
